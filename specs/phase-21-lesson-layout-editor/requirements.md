# Requirements — Lesson layout editor

## Context

Roadmap Phase 21, the last feature of the user's redesign canvas ([Piano Tutor — оновлений дизайн](https://claude.ai/artifact/8TBSo2UjJ2PTqZ4hoMbcrn), artboard `LayoutEditor`). The canvas shows a full-window editor titled "Lesson layout" ("This is how every lesson will look. Change the sizes while an example plays."): a staff preview, a panel with segmented choices for **keyboard height** (S / M / L / XL), **octaves on screen** (2 / 3 / 4) and **staff size** (S / M / L), two switches (**note names on keys**, **highlight the next note**), a "drag to change the keyboard height" handle above the piano, and **Reset** / **Done** in the header.

Today a lesson's piano has one height (176 px, 112 px on a phone held sideways), shows as many octaves as fit (white keys at least 40 px wide) plus every note of the lesson, and names every white key. A course lesson shows two lines of music (the current line and the next, `visibleSystems`) at one fixed scale; a built-in lesson shows one row of up to 8 notes, at most 576 px wide. Phase 20 added a settings store for every lesson (`piano-tutor.lessonSettings`: tempo, metronome, hint) and the Hint toggle; this phase adds the layout to the same store and reuses `hint` for the editor's "highlight the next note".

Added after the first review (user requests): a screen-size readout in the editor (FR-13); **a separate layout for each orientation** of the screen (FR-3); and **the number of rows of music and their height** (FR-7, FR-8), which replaces the canvas's "staff size".

Decisions made while planning (see the table at the end): the editor opens from **Settings** only (no new button in the lesson header); the example is a **silent built-in loop**; octaves are **Auto** (today's behaviour, the default) or a fixed **2 / 3 / 4**; note names are **off by default**, as on the canvas; rows are **the lines of a course lesson (1 / 2 / 3)**; **row height replaces staff size**; layouts are kept **per orientation on every device**.

## Functional requirements

### Opening the editor

- **FR-1** Settings must have a **Lesson layout** section with a one-line description and an **Edit layout** button. The button opens the editor as a full-window screen (no navigation rail or sidebar, like a lesson). The editor header has a **Back** icon button, the title and subtitle, **Reset**, and **Done**; Back and Done both return to Settings. The phone's or browser's Back gesture behaves as on the other screens (no history entry).

### The example

- **FR-2** The editor must show a built-in example the way a lesson shows it: a passage of two-staff music (treble melody, bass notes) in the course-lesson notation, long enough to fill three lines at the widest layout the editor offers, the piano below it, and a cursor that moves to the next step about every 0.75 s and starts over at the end. The keys of the current step light up and, when the hint is on, get the hint ring. The example makes **no sound**; keys pressed by the learner sound as everywhere else but change nothing. The loop stops while the editor is hidden (another tab) and, with `prefers-reduced-motion`, still steps but without animated scrolling.

### One layout per orientation

- **FR-3** The layout (FR-4 to FR-9) must be kept **separately for portrait and landscape**. The orientation is the window's: taller than wide (or square) is portrait, wider than tall is landscape. It applies to every device (a phone, a tablet, or a resized computer window). A lesson always uses the layout of the orientation the window is in now, and switches when the device is rotated or the window is resized across the square, with no reload and no lost progress in the lesson. Both layouts start with the same defaults (M, Auto, 2 rows, M, names off). The editor edits one layout at a time: a **Portrait / Landscape** switch at the top of the options panel chooses which, starting with the current orientation; the preview shows the chosen layout at the current window's size (it says so: "Shown at this window's size"). Rotate the device or resize the window to see the other layout in its own shape. The **hint** (FR-10) is not part of the layout: it is one setting for both orientations.

### The settings (each one belongs to the layout being edited)

- **FR-4 Keyboard height.** A segmented control **S / M / L / XL** (default **M**) must set the height of the lesson's piano: 140 / 176 / 216 / 256 px, and on a short screen (a phone held sideways, the existing `short` variant) 96 / 112 / 128 / 144 px. **M** is today's height. Black keys stay at the same share of the white keys' height as today. The section label above the preview's piano names the size ("Keyboard · medium").
- **FR-5 Drag to resize.** A handle between the preview and the piano ("Drag to change the keyboard height") must change the keyboard height by dragging up or down with a mouse, finger, or pen, snapping to the nearest of the four sizes while dragging (the segmented control follows). It is also a keyboard-operable slider: it is reachable with Tab, the arrow keys (and Page Up / Down, Home / End) move between the four sizes, and it announces the current size.
- **FR-6 Octaves on screen.** A segmented control **Auto / 2 / 3 / 4** (default **Auto**) must set how many octaves the lesson's piano shows. **Auto** is today's behaviour. With **2 / 3 / 4**, the piano is sized so that that many octaves (plus the closing C) fill its width, centred on the notes of the lesson (on the example's notes in the editor); white keys never become narrower than 40 px, so on a narrow screen a large count shows fewer octaves and the rest scrolls as on a phone today. When the lesson needs more octaves than chosen, the piano covers all of them and scrolls, and the view follows the current step as it does today.
- **FR-7 Rows of music.** A segmented control **1 / 2 / 3** (default **2**, as today) must set how many lines of music a **course lesson** shows at once: the line with the current step and the lines after it (with 1, only the current line). A built-in lesson has a single row and ignores this setting (the control's description says so). The notation box takes the height the rows need; when the rows do not fit between the header and the piano, the box scrolls up and down inside itself and keeps the current line in view, and the piano is never pushed off the screen.
- **FR-8 Row height.** A segmented control **S / M / L / XL** (default **M**) must set the height of each row of music by scaling the notation: 0.8 / 1 / 1.25 / 1.5 times today's size (**M** is today). It applies to a course lesson's score and to a built-in lesson's row. A larger size fits fewer bars on a line of a course lesson (the lines are laid out again for the narrower virtual width); a built-in lesson keeps its notes per page. It replaces the canvas's "staff size".
- **FR-9 Note names on keys.** A switch (default **off**) must choose between naming every white key (today's labels) and naming only the C keys (with their octave, as today) plus any key that is lit (pressed, sounding, or the example's current step). The computer-keyboard letters on the keys are unchanged in both cases.

### Hint, saving, reset

- **FR-10 Highlight the next note.** A switch must turn the lesson hint on and off. It is the same setting as the **Hint** toggle in the lesson header (Phase 20): changing one changes the other. It is the same for both orientations.
- **FR-11 Live and saved.** Every change must apply to the preview at once and be saved on the device in `piano-tutor.lessonSettings` (still `version: 1`; saved settings without the layout, such as those of Phase 20, get the defaults, and a field with an invalid value falls back to its default on its own, in each orientation separately). The layouts apply to every lesson (built-in and course lessons); Free play and the Library keep today's piano and notation.
- **FR-12 Reset.** **Reset** must set the layout being edited (keyboard height, octaves, rows, row height, note names) and the hint back to their defaults (M, Auto, 2, M, off, off) at once. The other orientation's layout, tempo, and metronome are not changed.

### Screen size readout

- **FR-13** The editor must show the current size of the window in CSS pixels and its orientation, as "Screen 844 × 390 px · Landscape", in a small badge in the header next to the subtitle (on a narrow screen under the subtitle), and the badge must update live when the window is resized or the phone is rotated. It is plain text for sighted users and is read out politely (`role="status"`), not on every pixel of a drag-resize (updates are throttled to one per 250 ms). It is a readout only: it changes no setting and is not saved.

### Layout of the editor

- **FR-14** From 1024 px wide (and on a phone held sideways) the options panel sits to the right of the preview, as on the canvas, and scrolls on its own if it does not fit. On narrower screens the options come first in one column and the preview (staff, handle, piano) below. Nothing scrolls sideways at 360 px except the piano itself (FR-6). The preview is drawn exactly like a lesson with the layout being edited.

## Non-functional requirements

- User-facing text goes through the translations module (English first; `uk`, `de`, `fr` too). The size letters S / M / L / XL and the counts are shown as they are in every language, with a translated accessible name (small, medium, large, extra large; "1 row", "2 rows", …).
- Works with the on-screen and computer keyboard (no MIDI device required); every control is reachable and operable by keyboard with visible focus rings; segmented controls report `aria-pressed`, switches use `role="switch"` with `aria-checked`; touch targets ≥ 44 px.
- Pure rules (settings parsing for both orientations, `orientationOf`, the size tables, the fixed-octave range, the number of visible rows, the snapping of a dragged height, the example's steps) live in `src/core/` with unit tests and no React, DOM, audio, storage, or timers.
- Changing orientation in a lesson must not restart it or change its state (the layout only changes how it is drawn).
- Colours only from theme tokens; no new runtime dependencies.
- No change to judging, scoring, saved progress, or lesson content. No perceptible added input latency.

## Out of scope

- A layout button in the lesson header or a layout panel over a running lesson (the canvas's header button; user decision: Settings only).
- Sound in the example, or a choice of example.
- Applying the layout to Free play or the Library (their piano and notation stay as they are).
- Free (non-snapping) keyboard heights; a layout per lesson or per device model; more than two layouts (for example by window width).
- Splitting a built-in lesson's page into several rows (user decision: rows are the lines of a course lesson only).
- Previewing the other orientation at its own shape without rotating the device or resizing the window.
- Hiding the computer-keyboard letters; note names in another convention.
