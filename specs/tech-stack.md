## Architecture rules

1. **One note pipeline:** every input source (MIDI, computer keyboard, on-screen keyboard, playback) emits the same note-on / note-off events into a single entry point. Sound, judging, and recording subscribe to it; nothing reads a device directly.
2. **Pure core:** music theory, note judging, lesson logic, and scoring live in plain TypeScript modules with **no React, DOM, or audio imports** so they are unit-testable.
3. **Thin UI:** components render state and forward events; they don't contain game rules.
4. **Shared types** live in one module; changing them requires checking every consumer.
5. **No new runtime dependencies** without a line in the feature's `plan.md` explaining why existing code can't do it.
6. Prefer small, dependency-free code for domain logic (e.g. a MIDI file parser) over heavy libraries.

## Conventions

- Docs, specs, code comments, commit messages, PR descriptions: **English**.
- UI language: **English** is the source and fallback language; the app also ships **Ukrainian, German, and French**. On first visit the language is detected from the browser (`navigator.languages`, primary subtag matched against `uk`/`de`/`fr`/`en`), otherwise English; a language the user picked always wins. All user-facing strings go through one in-house translations module with a locale per language (`en`, `uk`, `de`, `fr`); `en` defines the key type and is the fallback for any missing key. Messages support `{name}` interpolation, and plural entries are objects of forms (`one`, `few`, `many`, `other`) picked with `Intl.PluralRules` (`tp(key, count)`); percentages use `Intl.NumberFormat`. The chosen language is stored in `localStorage` (wrapped in try/catch). No hard-coded UI strings in components.
- Branches: `feature/<slug>`; one roadmap phase = one branch = one PR.
- Commits are small and reference the spec folder.

## Project layout

- `src/i18n/`: translations. `core.ts` (pure: locales, detection, lookup with `en` fallback), `storage.ts` (`localStorage` wrapper), `context.ts` (`useT()`, `usePluralT()`, `useLocale()`), `I18nProvider.tsx`, `noteNames.ts` (pure: note names per language; use it for any note name shown to the user), and `locales/{en,uk,de,fr}.ts`. Add new UI strings to `locales/en.ts` first; the key type comes from it.
- `src/core/`: pure domain logic with no React, DOM, or audio imports: shared event types (`types.ts`), note helpers, MIDI parsing, computer-key map, and held/sustained note bookkeeping, plus the lesson model (`lesson.ts`: steps, pages, judge, accuracy; a chord step is judged by the keys held at once), the curriculum and lesson generators with an injectable random source (`lessons.ts`: `LESSON_UNITS`, the derived `LESSON_CATALOG`, `nextLessonId`), the staff geometry (`staff.ts`: note → clef, line index, ledger lines; `spellNote(note, clef)` places a note on a chosen staff), and the layout of one page of steps (`staffRow.ts`: x slots, chord stacking, seconds, merged ledger lines), plus the on-screen piano layout (`keyboardLayout.ts`: which keys fit a width, 40 px minimum white key, A0–C8 limits, pixel boxes per key, scroll target; `include` adds the range of a piece that is playing), the MIDI file reader and the playback schedule (`smf.ts`, `playback.ts`), and the MusicXML import (`xml.ts` minimal XML reader, `zip.ts` zip directory + score lookup, `musicxml.ts` → the same `Piece`, with `PieceNote.hand` taken from the staff; `contentHash.ts` for the id of a file), and the notation reduction with its system layout (`score.ts`, `scoreLayout.ts`: bars, one voice per staff, rests, ties, sharps, and the time-to-x map of the cursor), plus the library: the catalogue of pieces and composers (`libraryCatalog.ts`, pure data), the browsing rules and policy allowlists (`library.ts`), and the learner's marks (`libraryMarks.ts`). Unit-tested. The computer-keyboard layout covers `A`–`;`, `W E T Y U O P`, and `ShiftLeft` for the B below the base C (the on-screen piano has 26 keys).
- `src/input/`: the note pipeline (`noteBus.ts`) and its adapters: computer keyboard, Web MIDI, key labels, plus `NoteInputProvider` and hooks.
- `src/audio/`: the Web Audio synth and volume/mute settings.
- `config/`: build configuration. `buildInfo.ts` (pure, unit-tested) resolves base path, commit, and host from environment variables (`BASE_PATH`, `DEPLOY_TARGET`, `GITHUB_SHA`, Cloudflare `CF_PAGES*` / `WORKERS_CI*`); `vite.config.ts` exposes it to the app as `__BUILD_INFO__`. `wrangler.jsonc` at the repo root configures the Cloudflare deployment.
- `src/lesson/`: `useLesson` hook that connects a lesson to the note bus (synchronous judging, short right/wrong feedback, restart, octave save/restore, an `onFinish` callback called once).
- `src/playback/`: the MIDI file player. `player.ts` (clock-driven; emits `noteon` / `noteoff` / `sustain` on the bus with source `playback`; injectable clock; releases every held note on pause, stop, seek, a new file, the end, and unmount), `loadScoreFile.ts` (reads a chosen `File`, size checked first; detects MIDI, `.mxl` zip, or MusicXML text by content; inflates with `DecompressionStream`, 20 MB limit; returns `file-<hash>` as the id), `context.ts` + `PlayerProvider.tsx` (the player and the open file for the whole app).
- Voices (Phase 16): `PieceNote.voice` (2 = the lower voice; unset otherwise and for MIDI), ranked per staff in `musicxml.ts` (`rankVoices`); `score.ts` builds each voice separately (`voiceColumns`) and joins them per bar (`joinVoices`), marking `Column.voice`, `stem`, `restShift`, and `offset`. Every other consumer reads the staff's columns in unit order and keeps working; `beamGroups` and `ScoreView` look at `voice` / `stem`.
- `src/core/beams.ts` (pure, unit-tested) decides which eighth and sixteenth columns are beamed (`beatUnits`, `beamGroups`: groups per bar and staff within a beat, the group's stem direction, second beams, hooks) and where the beam runs (`beamLine`, `heightAt`: slope at most one staff space, every stem at least the minimum length). `ScoreView` draws them (`beamsOfSystem`, `BeamsView`); the score model and the layout do not know about beams.
- `src/core/spelling.ts` (pure, unit-tested) decides how notes are written: `spell` (the spelling from a MusicXML file when it matches the pitch, else flats in a key with flats and sharps otherwise), `keyAlterations`, `keySignatureIndexes` (standard places of the signs; bass = treble − 14 steps), `staffIndex`, `spellingFor`. `Piece.keySignatures` and `PieceNote.spelling` carry the key and the written spelling from the readers; `ScoreBar.keySignature` / `showKeySignature` and `ScoreNote.alter` carry them into the score; `measureBars` / `gapStepsFor` (in `score.ts`) give the space between the staves that `ScoreView` and `StaffView` both use (each staff on its own vertical axis); `scoreLayout` reserves key-signature room (`keyWidth`, `LayoutBar.keyX` / `keyRoom`).
- `src/core/keyboardRange.ts` (pure, unit-tested) is the size of the learner's real keyboard: the `KeyboardRange` (`null` = not set), the six key counts with their default ranges, octave shifts inside A0–C8, the calibration steps (lowest key, then highest), `notesOutside` (distinct pitches of a lesson outside the range) and the saved-range parser. `src/keyboard/`: `storage.ts` (`piano-tutor.keyboard`, versioned JSON, try/catch), `context.ts` + `KeyboardRangeProvider.tsx` (one global range), and `useCalibration.ts` (subscribes to the note bus only while calibrating and counts only `noteon` with source `midi`). The Keyboard panel is `KeyboardSizeControl`, rendered by `MidiStatus` (hidden while a lesson is open); `PianoKeyboard` dims keys outside the range and `LessonScreen` shows the out-of-range notice.
- `src/library/`: the library adapters. `loadLibraryPiece.ts` (fetches a piece from the app's own static files under `import.meta.env.BASE_URL`; a failed request or an HTML fallback page is `network`), `storage.ts` (`piano-tutor.library`, versioned JSON, try/catch), `context.ts` + `LibraryMarksProvider.tsx`. The files are in `public/library/<composer>/*.mid` and `public/library/portraits/*.jpg`; `licenses/library-sources.md` records the source, licence, and check date of each. **Library content policy (user decision):** MIDI files only from the Mutopia Project and only pieces whose own page says Public Domain; portraits only from Wikimedia Commons images marked Public domain (or CC0); no composers of Russian origin. Tests enforce the licence and host allowlists and read the real files (`config/libraryFiles.test.ts`, in `config/` because that project has the Node types).
- **Sample licence policy (Phase 17, user decision):** piano samples only from a set whose own source page says CC0 or public domain; never CC-BY, CC-BY-SA, or custom licences. Record the source, the verbatim licence sentence, the version, the check date, and the changes in `licenses/piano-samples.md`; read the source page again before committing samples. The brand of the recorded piano appears only in `licenses/` and the README credits, never in the UI or manifest. A test (`config/pianoSampleFiles.test.ts`) enforces the record, the file sizes, and the brand rule. The current set is FreePats **Upright Piano KW** (CC0 1.0).
- `src/audio/` and `public/piano/` (Phase 17): `synth.ts` is the sampler behind the same `Synth` interface (`resume`, `setVolume`, `setMuted`, plus `setReverb` and a load status); `sampleLoader.ts` fetches and decodes `public/piano/*.mp3` at app start (keys are silent until ready, with a loading / failed text and Retry). The pure rules (`src/core/pianoSamples.ts`: `pickSample`, `releaseTime`, `onsetIndex`, `impulseResponse`) and the generated map (`src/core/pianoSampleMap.ts`) have no audio imports.
- `src/core/course.ts` (pure, unit-tested) turns a piece's `Score` into a course: parts, stages (right, left, both hands), drills, merges, stable lesson ids (`melody:<pieceId>:<hand>:<kind>[-n]`), and the Home helpers (`finishedLessons`, `piecesInProgress`). `src/course/`: `loadCourse.ts` (library file → `buildScore` → `buildCourse`), `context.ts` + `CourseProvider.tsx` (the open **source**, a library piece or a file opened from disk, and a cache of built courses; a file source needs no fetch). `Lesson` has optional `hand`, `pieceTitle`, `titleParams`, and `notation` (`{ score, stepTimes }`); the judge ignores them. `NotationView` draws a lesson's notation with the Player's `ScoreView`, and `CourseScreen` / `LearningPieces` are the course UI. `config/libraryCourses.test.ts` builds the course of every library piece from disk.
- `src/pwa/`: thin PWA adapters. `installPrompt.ts` (captures `beforeinstallprompt`, imported from `main.tsx` before render), `usePwaUpdate.ts` (`virtual:pwa-register/react`), `useInstallHint.ts`, `storage.ts` (`piano-tutor.installHint`), and the pure rule `installHint.ts` (unit-tested). The banners and the install card are `PwaNotices`, `UpdateBanner`, `OfflineReadyNote`, and `InstallCard` in `src/components/`.
- `public/`: `icon.svg` (source) and the generated icons; `pwa-assets.config.ts` at the root configures the generator.
- `src/progress/`: progress persistence and state. `storage.ts` (`localStorage` key `piano-tutor.progress`, versioned JSON, try/catch), `today.ts` (local `YYYY-MM-DD`), `context.ts` (`useProgress()`), `ProgressProvider.tsx`. The rules are pure, in `src/core/progress.ts` (stars, XP, levels, streak, `recordRun`, `parseProgress`) and `LESSON_CATALOG` in `src/core/lessons.ts`.
- `src/components/`: thin UI components, including `PlayerScreen` (the Player mode), `LibraryPanel` / `PieceInfo` / `Portrait` / `MarkToggles` / `DifficultyDots` (the library UI), `ScoreView` (SVG score of two visible systems; glyph outlines in `notationPaths.ts` from Bravura), `PianoKeyboard` (full-window-width piano drawn from `keyboardLayout`, octave ruler when it scrolls; `useElementWidth` is its ResizeObserver hook) and `StaffView` (SVG grand staff with a row of steps; clef outlines in `clefPaths.ts` come from the Bravura font, SIL OFL 1.1, see `licenses/`), `LessonScreen`, `LessonSummary`, and `ModeSwitch`. The screen (Home / free play / open lesson) is plain app state; there is no router.
- Tests sit next to the code as `*.test.ts`. The Vitest environment is `node`. There is no DOM test setup yet.

## Known technical debt

- The keyboard size (Phase 12) is verified only manually (the panel and the lesson notice at 360 px, the dimmed key contrast, calibration with a real MIDI keyboard); the range rules are unit-tested. The range is one global setting, not per device, and nothing uses it yet to choose or transpose lessons.
- MusicXML import (Phase 13) is covered by unit tests on scores built in code and was not yet checked against a corpus of real MuseScore exports. It ignores tempo marks (fixed 120 bpm), repeats, grace notes, and several voices per staff; `.mxl` needs the browser's `DecompressionStream` (Chromium has it). Courses from a file on disk are not kept between sessions, only their stars.
- `typescript` is pinned to `^6` because `typescript-eslint` doesn't support TS 7 yet. See `backlog/tooling.md`.
- Prettier uses `endOfLine: "auto"` and there is no `.gitattributes`, so Windows checkouts get CRLF warnings. See `backlog/tooling.md`.
- UI behaviour (language switching, layout, the staff row at 360 px, chords on touch) is verified only manually; there are no component or e2e tests.
- Locale translations (`uk`, `de`, `fr`) are written by the agent and need a human skim in every phase that adds strings.
- `midiAccess.ts` was verified by hand on one keyboard (Roland FP-30X) in Phase 3, not by automated tests. Other keyboards may differ (for example half-pedal values).
- Progress persistence (`src/progress/`) and the Home screen are verified only manually; the pure rules are tested.
- Two browser tabs each keep their own copy of progress; the last save wins (no `storage` listener yet).
- The responsive piano (full width, scrolling, follow-scroll, key release on resize) is verified only manually; the layout rules are unit-tested.
- The library's licence check is manual per piece (read on the piece's own Mutopia page; the tests enforce the recorded data, not the website), and "Public Domain" is the contributor's declaration on Mutopia and Commons, not a legal guarantee. Portraits are cropped by hand. The files are mechanical renderings of the score (exact rhythm, no expression), and some Mutopia files carry a default 60 bpm.
- The library UI (panel, filters, marks, portraits, offline caching of opened pieces) is verified only manually; the rules and the catalogue are unit-tested.
- Courses (screen, notation in lessons, Back to the course, the Home section) are verified only manually; the course builder is unit-tested, including a build for every library piece. The hand of a note comes from the staff of a MusicXML file, or from the middle-C split for MIDI, so a MIDI melody that crosses it may land in the other hand. Lessons judge pitches only, not timing, and cover only the first 6 parts of a piece.
- The Player (clock timing against real audio, the score view, and the follow-scroll of the piano) is verified only manually, with files the user picked; the parser and notation are tested with MIDI bytes built in code, not with a corpus of real files, so unusual files may show a poor reduction (no tuplets; MIDI files and MusicXML staves without `<voice>` are one voice per staff). Two voices per staff are drawn only from MusicXML `<voice>` (voices 3–4 merge into the nearer one); their drawing was checked by rendering a small score with headless Chrome, not with a corpus of real exports. Beams are computed by beat for every file (MusicXML `<beam>` is ignored), so their grouping can differ from the printed edition; beam drawing was checked by rendering with headless Chrome, not by component tests. MIDI files are spelled by the sign of their key only (no harmonic analysis), so chromatic passages can get the other enharmonic spelling; key changes draw no cancelling naturals. The key-signature drawing and the space between the staves were checked by rendering with headless Chrome, not by component tests.
- Playback uses timers, which browsers slow down in a background tab; it does not drift, but notes can be late there. A Web Audio look-ahead would fix it (the note bus has no timestamps yet).
- The service worker, offline mode, the update banner, and the install flow are verified only manually (on `bun run preview` and the deployed sites); only the install-hint rule is unit-tested.
- Input adapters, the synth, and components have no automated tests (Web MIDI, Web Audio, and DOM are not available in the `node` test environment).
